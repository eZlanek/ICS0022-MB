# Password Manager - Design Document

## Purpose
The application will run locally through the terminal without an internet connection. It will store service names, usernames, and passwords in an encrypted file on the user's computer.
The user enters a master password to access the vault. Entries are decrypted in memory for the duration of a command. Passwords remain hidden when listing entries, but the user can explicitly request the password for a selected entry. Adding, updating, and deleting entries will also be supported.
A graphical interface, cloud or centralised storage, network connections, and importing or exporting other password managers' formats are outside the project scope.
## Architecture
- CLI: accepts commands and user input, forwards requests to other modules, and displays results.
- User-management module: allows access to entries after the vault has been successfully unlocked.
- Entry-management module: performs operations on entries and validates input.
- Encryption module: derives the key from the master password, verifies authenticity, and encrypts and decrypts entries.
- Storage layer: reads the vault file and saves changes.
When saving, updated entries are encrypted and written to a temporary file together with the header. After a successful write, the temporary file atomically replaces the original. If writing fails, the original file is preserved. Viewing entries does not require saving the vault again.

Flow: 
The CLI receives a command and requests the master password.
The storage layer reads the vault header and encrypted data.
The encryption module derives the key using Argon2id, then verifies
and decrypts the vault using XChaCha20-Poly1305.
If verification succeeds, the user-management module allows the
requested operation on the decrypted entries. The CLI displays
the result without revealing passwords unless explicitly requested.
If verification fails, access is denied and the file remains unchanged.
## File Format and Cryptography
The public header contains the format version, algorithm identifiers and parameters, salt, and nonce. Entries are stored as ciphertext with an authentication tag. The header is also covered by the authenticity check.
Argon2id derives the key from the master password, salt, and parameters. XChaCha20-Poly1305 uses this key for authenticated encryption. A fresh random nonce is generated for every save. The master password and key are never intentionally written to disk.
## Main Threats
- Master-password guessing: use a long, unpredictable password and computationally expensive Argon2id settings.
- File modification: verify authenticity; on failure, deny access without modifying the file.
- Memory access: minimise the lifetime and number of copies of secrets and explicitly clear sensitive buffers.
- Screen observation: hide password input and reveal stored passwords only on explicit request.
These measures reduce risks but cannot fully protect against malware with sufficient privileges.
## Technologies
The application will use C++17 and libsodium. Using established cryptographic implementations reduces development time and the risk of mistakes compared with implementing the algorithms myself.
